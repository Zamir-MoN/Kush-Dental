# Observability & Monitoring Strategy

## Objective
Ensure high availability and rapid incident response by tracking the health, performance, and error rates of the Kush Dental Clinic backend and frontend.

## 1. Health Endpoints
Explicitly separate liveness from readiness to avoid false-positive container restarts:
- **`GET /health/live`**: Returns 200 OK if the Express application process is running. Does NOT check the database.
- **`GET /health/ready`**: Returns 200 OK if the application is fully ready to serve traffic (checks database connectivity via a simple `SELECT 1`).

## 2. Metrics & APM (Application Performance Monitoring)
- Monitor API latency, specifically the `POST /appointments` and database queries.
- Track HTTP 5xx error rates to detect systemic backend failures.

## 3. Structured Logging
- Application logs must be structured as JSON.
- Every incoming HTTP request should be assigned a `correlationId` (e.g., `x-request-id` header) that is passed down through the service layer and included in all logs generated by that request.

## 4. Error Tracking
- Unhandled exceptions and promise rejections must be caught and reported via a centralized error tracking tool (e.g., Sentry).
- The Express global error handler must format errors consistently and prevent stack traces from leaking to the client in production.

## 5. Alerting
- Configure alerts for:
  - Liveness probe failure.
  - High 5xx error rate (> 5% of traffic over 5 minutes).
